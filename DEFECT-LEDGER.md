## DL-B001 · 2026-07-25 · The app-class bundle the order sends the Worker to read is empty
**What happened.** `CONTEXT.md` step 7 orders the Docker/Traefik wiring built "per the class
bundle in `/docker/v2s-canon/_library/`". There is no bundle. Every app-class directory under
`_library/reference/by-app-class/` is absent — the directory holds a single empty `.gitkeep`.
The Implementation Guide's Customization Pass step 2 depends on the same path ("Pull the bundle
for that class from `/docker/v2s-canon/_library/reference/by-app-class/`"), so this is not a
mis-worded order, it is a missing canon artifact the doctrine assumes exists.

**Named cause.** *(First guess — "wrong path in `CONTEXT.md`" — falsified by contrary test:*
`CONTEXT.md`'s path matches the Implementation Guide's path exactly, and both resolve to a real
directory, so the pointer is right and the target is empty. The fault is not the reference.*)*
The named cause is that canon's **library of app-class reference bundles was never populated**,
while three separate doctrine artifacts (Impl. Guide Customization Pass, Blueprint §14's tree,
and IODE's generated `CONTEXT.md`) already instruct the Worker to build from it. Doctrine that
points at an empty shelf will silently produce *whatever each Worker improvises*, which is the
opposite of the standardisation the bundle exists to provide — the divergence will be invisible
because each project's wiring will look locally reasonable.

**Artifact fix (this project, closed).** Built the wiring to the **observed fleet as-built
pattern** instead of improvising: read `/docker/traefik/traefik.yml` and
`/docker/traefik/docker-compose.yml` and matched them exactly — external `traefik-public`
network, `letsencrypt` certresolver, `websecure` entrypoint, `exposedByDefault: false` so every
route is an explicit opt-in label. Then added the audit-tier-high hardening the class calls for
(no published host port, non-root user, read-only rootfs + tmpfs, all capabilities dropped,
no-new-privileges, HSTS/nosniff/frameDeny at the edge, log rotation). Every choice is recorded
in `DECISIONS.md` so a future bundle can be diffed against what was actually built.

**Class fix (raised, NOT closed).** Populate `_library/reference/by-app-class/` — at minimum a
`multi-tenant-saas/` bundle carrying the Docker/Traefik baseline, the tenant-isolation
checklist, and the audit tier. Until then, every project standup improvises this layer.

**Status: open — class fix raised for the Tone canon route; project-level fix closed-verified**
(bridge health green, wiring verified end to end — see `BUILD-REPORT.md`).

## DL-B004 · 2026-07-25 · The Architect could not rewrite any file the Worker had created
**What happened.** Found by probe during standup verification, before hand-off. The bridge runs
as uid 1000 (non-root, correctly). The Worker writes `/docs` natively as root, so every file it
creates is mode 644 **root:root**. The bridge could *read* those files but **not open them for
writing** — reproduced directly: `echo x >> /docs/_roottest.md` inside the container →
`Permission denied`, and `write_doc` on a root-created file failed the same way.

**Why this was severe, not cosmetic.** Canon's session baton requires the Architect to **rewrite
`STATE.md`'s top to current truth as the last act of every session**
(`chat-operating-instructions.md` §0) — and `STATE.md` is a file the *Worker* created at standup.
The append-only ledgers are the same shape. So the doctrine's single most-repeated Architect act
would have failed on the first attempt, on every project standing up this way, at the moment the
baton was supposed to be handed over. It would have looked like a broken bridge rather than a
permissions mismatch.

**Named cause.** *(First guess — "the docs directory ownership is wrong" — falsified by contrary
test: the directory was already `chown`ed to 1000:1000 and the bridge could create NEW files in
it perfectly well. Ownership of the directory was right; the failure was per-FILE.)* The named
cause is that **two writers with different uids share one directory, and the write path used
required permission on the FILE** (`open` for write / `O_APPEND`), which the second writer can
never have on the first writer's files. A `chown` after every Worker write would "fix" it only
for as long as everyone remembers — a ritual, not a fix, and one whose failure is silent until an
Architect session close.

**Artifact fix (closed-verified).** Rewrote both write paths to **temp-file-then-`rename`**
(`docs-root.ts:atomicWrite`). `rename()` requires permission on the **directory**, not on the
target file — and the directory is owned by uid 1000 — so writes now succeed regardless of which
uid created the file, with no chown ritual for anyone to forget. `append_doc` became
read-modify-atomic-write for the same reason. Two further gains fell out of it: writes are now
**atomic**, so a crash or full disk can never leave a half-truncated record (these files are the
project's record), and the temp file is removed on every failure path, not just the happy one.
In-flight temp files are hidden from `list_docs` and `search_docs`.

**Re-verified after the fix:** `write_doc` over a 644 root:root file → succeeded; `append_doc` on
a root-created file → succeeded and preserved the existing content; no temp files left behind;
and **containment re-tested** (path traversal and symlink-escape write both still refused,
`/etc/passwd` unmodified) to confirm the fix did not widen the wall.

**Class relevance — worth canon knowing.** Any project bridge that runs non-root over a directory
the Worker also writes has this defect. It is not binjreel-specific, and the naive fix (run the
bridge as root) trades it for a much worse one. Raised alongside DL-B001–B003 for the Tone canon
route: the app-class bundle, when it is written, should carry the atomic-write requirement for
bridge write paths.
**Status: closed-verified (project) · class note raised.**

## DL-B005 · 2026-07-25 · Project PAT placement overwrote the shared box credential; canon read regressed
**What happened.** The Director placed the `github-pat` for `papamg/binjreel`. Afterwards
`git -C /docker/v2s-canon pull` — which ran clean at L-000 — fails with *could not read Username*,
and `git ls-remote` fails identically on **both** `papamg/binjreel` and `papamg007/v2s-canon`. The
Worker opening the v0.1 build therefore could not pull canon and read doctrine from the local
clone at `ab07022` (clean tree, the same commit L-000 verified) without being able to confirm it
against `origin/main`.

**Observed state.** `/root/.git-credentials` (0600 root:root, mtime 18:19) holds **exactly one**
entry, and that entry is **host-only** — `https://<redacted>@github.com`, no repository path.
The box sets `credential.usehttppath=true` **globally** (and the app repo carries a local
`credential.helper=store --file=/root/.git-credentials`). Git therefore requests credentials keyed
host **+ path**; a stored entry with no path matches no path-qualified request, so the helper
returns nothing and git falls back to prompting.

**Named cause.** *(First guess — "the PAT is invalid or expired" — **falsified by contrary test**:
a bad credential makes GitHub challenge and refuse, producing `Authentication failed` / `403 Write
access to repository not granted` — which is precisely what DL-B003 observed for push at standup.
The observed error is `could not read Username`, which is git finding **no credential to present**.
The failure is a **lookup miss, not a credential rejection**, so the token's value is not
implicated.)* *(Second alternative — "canon is public and never needed auth, so nothing regressed" —
**also falsified**: unauthenticated, `papamg007/v2s-canon` returns **404**, so canon is private, so
its clean pull at L-000 proves a working canon credential existed in this same file and is now
absent.)* The named cause is that **a per-project `git-credential` placement replaced the shared
box credential file rather than appending a path-keyed entry to it** — and, because the replacement
is host-only while the box is path-keyed, the result authenticates **nothing at all**, not even the
repo it was placed for.

**Class relevance — this is the predicted failure, and worse.** `procedures/secret-manifest.md`
("Slot scope") and DECISIONS.md **D-005** both state that a `git-credential` on a shared box is a
BOX-LEVEL slot and that a per-project placement "silently overwrites the box credential and breaks
every other repo." That is exactly what occurred. D-005 further reasoned that because
`useHttpPath=true` was already set, a path-keyed `papamg/binjreel` entry "would not in fact
collide" — correct as far as it went, but it assumed the placement *would be path-keyed*. The
placement path itself carries no such requirement, so the safeguard the box was relying on was
never actually engaged. **The gap: `useHttpPath=true` protects against collision only if every
stored entry carries a path, and nothing in doctrine or tooling enforces that at placement time.**

**Artifact fix — NOT taken by the Worker (Director's act).** Restoring this requires secret values:
canon's read token is not on this box in any recoverable form, and re-placing is an Owner's-hands
act (Framework §0/§4 — issue PATs, hold root credentials; D-005 — "the safety of adding an entry is
the Director's to confirm at placement, and the failure mode of guessing wrong is fleet-wide").
Recommended repair, handed up as finished work: two **path-keyed** entries matching the remote URLs
exactly, including the `.git` suffix git actually sends —
`https://<user>:<token>@github.com/papamg007/v2s-canon.git` and
`.../papamg/binjreel.git`. The Worker offered to append the path to the existing entry in place
(a suffix edit that never prints or handles the value), which would restore **binjreel push only**.
Rejected alternative: setting `credential.usehttppath=false` — it would make the host-only entry
match, but points one credential at every GitHub repo on the box (the fleet-wide blast radius D-005
exists to prevent) and would still 403 on canon if the PAT is fine-grained to `papamg/binjreel`.

**Build impact: none.** v0.1 commits to `binjreel-dev` locally (`CONTEXT.md`, Build discipline);
STATE already carries push confirmation as a Director act "neither blocking the build start." The
real cost is doctrinal, not mechanical: **canon-first could not be honoured as written** for this
session, and that is recorded here rather than papered over.

**Class fix (raised, NOT closed).** Placement tooling/doctrine should require a `git-credential`
entry to be **path-keyed on a box with `useHttpPath=true`**, and should **append rather than
replace** the shared store. Route with DL-B001/B002/B003 via the Tone canon drop.

**RESOLUTION · 2026-07-26 — project instance closed-verified.**
**Cause confirmed as named:** host-only placement on a path-keyed box. Corrected by the Director to
the intended path model — an account-level `papamg` write path plus a box-level read path to
`papamg007/v2s-canon`. The Worker placed **nothing**; no credential file was read or printed.

**Closed by observation, per the manifest rule that a slot reaches `verified` only by observing the
secret *work*:**
- **Canon read** — `fetch` exit 0, HEAD `834fc98`, and `ls-remote origin HEAD` (a network
  round-trip, unservable from local objects) returned the identical SHA with `FETCH_HEAD` written
  in-run. The clone is **2 commits ahead** of the `ab07022` the v0.1 build was pinned to, so the
  doctrinal cost this entry recorded was real, and is now paid off.
- **binjreel write** — `push … refs/heads/_writecheck` → `* [new branch]`; `push --delete` →
  `- [deleted]`; remote returned to `main` @ `ec2ef3d1` with no ref left behind. The DL-B003 push
  symptom (`403 Write access not granted`) did **not** recur.

Raw evidence: `BUILD-LEDGER.md` **L-022**. STATE **W-001** cleared.

**What this resolution does NOT cover — deliberately.** The verification proves `papamg/binjreel`
pushes; it does **not** prove an account-level `papamg` credential, because under
`useHttpPath=true` a path-keyed entry matches one path only. That gap is the *same* mechanism this
defect is about, one level up, and is carried as STATE **W-002** rather than folded into this close.
Branch protection on `main` also remains unconfirmed — a throwaway ref would not have challenged it.

**Status: RESOLVED (project instance, closed-verified 2026-07-26) · class fix STILL OPEN — nothing
in doctrine or tooling yet enforces path-keyed, append-not-replace placement, so the same failure
remains available on the next box.**

## DL-B006 · 2026-07-27 · v0.2 playback signing used a single-FILE token; HLS died at the edge (caught at GATE-3)
**What happened.** The v0.2 signer signed the exact manifest path `/{guid}/playlist.m3u8`. HLS is
not one file: the master playlist references sub-playlists (`360p/video.m3u8`, …) which reference
segments (`video0.ts`, …), all at sibling paths under `/{guid}/`. A single-file token covers none
of them, so the player's very first follow-up request 403'd. The contract tests could not catch
this — they verified the token against our own recomputation, and both sides shared the same
wrong assumption; only the real edge (GATE-3, keys placed) could refuse it. The v0.2 signer's
comment even asserted segments would be "validated against the same token via its directory
scope" — an assumption, recorded as if it were a property.

**Named cause.** The signer was built from the summary form of Bunny's token algorithm (single
path, `sha256(key + path + expires)`) rather than from the vendor's reference implementation.
Two things the summary omitted: (1) HLS requires a DIRECTORY token (`token_path = /{guid}/`),
and (2) `token_path` must participate in the SIGNED DATA, not just ride the URL — proven at the
edge: the same directory token WITHOUT `token_path` in the hash is refused (probe C, 403), with
it accepted (probes A/B, 200).

**Fix (verified against the vendor's current reference, then against the live edge).**
`signer.ts` now mirrors `BunnyWay/BunnyCDN.TokenAuthentication` (nodejs/token.js) for our
parameter set: `token = "HS256-" + base64url(HMAC-SHA256(key, token_path ‖ expires ‖
"token_path=" + token_path))`, emitted in the path-based form
`https://{host}/bcdn_token={token}&token_path={enc}&expires={exp}/{guid}/playlist.m3u8` — so
every relative reference a player resolves stays under the authenticated prefix and inherits
auth. (The legacy non-HMAC concat form also passes at the edge — probe B — but the HMAC form is
the current documented scheme; the old form is superseded, D-016.)

**Proven live, all three ordered checks** (episode `e58a8a9e…`, video `b56ffcb4…`):
manifest **200** with valid m3u8 · referenced sub-playlist **200** AND a real media segment
**200 (351,560 bytes)** under the SAME token — the exact case the single-file token 403'd ·
expired URL **403**. Plus unit tests recomputing the reference algorithm independently (87/87).

**Discovery adjacent to the defect, handed up (zone config, not code): the pull zone 403s any
request with NO `Referer` header** — any non-empty referer passes (even a foreign one), empty is
blocked. Probes 2/3 proved it: identical signed URL, 403 bare, 200 with a referer. This is a
Bunny zone setting, not our signer. **It will break native mobile players** (they typically send
no referer) — the Director should review that setting before v0.3's player work; as a
hotlink-protection measure it currently blocks curl-without-headers and nothing else.

**Method note (secret custody).** Diagnosis required testing candidate token constructions
against the live edge, which requires the signing key. The key was read into process memory
inside a throwaway container (exactly as the app itself reads it) and used to compute tokens;
**no value was printed, logged, or written anywhere** — outputs were HTTP status codes only.

**Status: closed-verified (live at the edge) · fix committed on `binjreel-dev` · referer-setting
question open on the Director.**

## DL-B007 · 2026-07-27 · Playback TTL default (30s) is shorter than a viewing session; playback died mid-episode
**What happened.** GATE-3 live viewing (Director, VLC): playback started and then died partway
through the episode. The signed directory token (DL-B006 fix) correctly covers every segment
path — but it expires as a whole, and the default `PLAYBACK_URL_TTL_SECONDS=30` outlives only
the first seconds of segment fetches. An HLS player keeps requesting segments under the same
signed prefix for the entire episode; when the token lapsed, the edge began 403ing
mid-stream.

**Named cause.** The 30-second default was chosen for the anti-sharing property ("a leaked URL
is dead before it can be shared") on the implicit assumption that the URL is consumed ONCE, at
playback start. That assumption was true of the v0.1 stub's shape and false of real HLS: the
token must stay valid across the WHOLE session's segment fetches, not just the manifest read.
The v0.2 contract tests could not catch this — they verify the mint, not a minutes-long
consumption pattern; only real playback could.

**Operational fix (Director, done).** `PLAYBACK_URL_TTL_SECONDS=3600` set in `app/.env`;
config-driven by design (the value was always the Director's dial, never compiled in), so no
code changed and no redeploy of source was needed. Live VLC playback confirmed after the change.

**Code follow-up (OPEN — next code touch, deliberately not done in this docs-only pass).** The
CODE DEFAULT in `src/config.ts` (`intWithDefault('PLAYBACK_URL_TTL_SECONDS', 30)`) still says
30 — a fresh deploy that omits the env var would silently reintroduce mid-episode death. Raise
the default to a session-length value (e.g. 3600) at the next code touch.

**Product decision (OPEN — Director).** The final TTL is an anti-sharing vs viewing-session
tradeoff (a leaked URL now works for up to an hour). Options if a shorter horizon is ever
wanted: player-side re-mint on expiry (v0.3 can refresh the URL mid-session), or per-quality
tokens. Not engineering's call; recorded for the TDD §12 list.

**Status: closed operationally (env, live-verified) · code-default fix open (next touch) ·
final TTL open (Director product decision).**

**CLOSED FULLY 2026-07-28 (v0.3 build).** Both engineering halves landed per CONTEXT v0.3 §9:
the code default in `src/config.ts` is now **900s** (env still overrides; the box keeps 3600),
proven by a test that fails if the 30s ever returns; and the **mid-session re-mint seam** exists
(`POST /v1/episodes/:id/playback/renew` — same mint path, full entitlement re-check every call,
zero ledger movement, all by test). The player can now hold ANY TTL the Director picks and renew
mid-session — so the final-TTL product decision (TDD §12) is no longer time-pressured.
**Status: CLOSED (code + seam) · final TTL value remains the Director's dial, unblocked.**

## DL-B008 · 2026-07-28 · /admin screen layer rendered without asserting the session first
**What happened (Architect finding, deployed code).** The `/admin/api/*` seam was correctly
gated — 401 without the session cookie, ops refusing until the forced change, D-014 token
server-side only — but SCREEN-level auth was never asserted anywhere: the server hands the
full SPA shell + bundle to anyone at /admin, and the only thing standing between a stranger
and admin UI was client component state that no test had ever exercised. Consequence as
found: the Owner was never routed through the forced password change; the seeded temp
credential was still live.

**Reproduction (Worker, headless browser against the deployed site, clean profile).** The
fresh-load login card DID render in reproduction — the top-level client gate held on that
path. What reproduction CONFIRMED at the screen layer: (1) the /admin route fired a VIEWER
session bootstrap (`POST /v1/auth/anonymous`) before/independent of session resolution — the
lobby was partially furnished to a stranger; (2) the gate lived INSIDE one screen component
(per-screen convention, not structure) — any future admin subroute would render ungated by
default; (3) no test at any level asserted what a browser renders at /admin, so none of this
class could fail a suite. Exposure while open: no writes, no private data, no secrets — the
API seam refused everything (verified then and now); the reachable surface was the admin
screen scaffolding and one anonymous viewer account minted per visit.

**Named cause (the traceback).** The v0.4 DoD said "forced password change on first login
ENFORCED" without naming the SURFACE on which enforcement must be proven. The Worker read it
at the API seam (where it was tested six ways) and never asserted it at the screen — API-level
auth verified, screen-level auth never asserted. A DoD line that names a property without
naming its surface gets proven on the surface that is cheapest to test.

**Fix (this order, web face only — no API change, no ledger, no design).**
- `src/app/admin/_layout.tsx` — THE GATE, structural: every route under /admin renders
  through it. Session resolves FIRST (exactly one call, `GET /admin/api/me`); no session →
  ONLY login; mustChangePassword → ONLY the change screen (eye-reveal on every field), and a
  successful change lands back at login (all sessions revoked) — never a shortcut in; valid
  session → the panel routes. The root layout skips the viewer bootstrap on /admin entirely.
  Panel ops that meet a 401/403 mid-session call the gate's `invalidate()` — no stale
  furnished panel on a dead session.
- **The missing test class added:** a Playwright screen-level suite (`web/e2e/`) drives the
  REAL exported bundle in a REAL browser — fresh /admin asserts login-screen-only AND that
  the ONLY network call is the session resolve (zero ops, zero /v1); a must-change session
  asserts change-screen-only; the full journey asserts temp login → forced change → temp
  credential dead → new credential → the panel; the eye-reveal is asserted working. 4/4.

**Re-verified LIVE at the screen level (clean-profile browser, not curl):** /admin renders
the login form and nothing else — login screen 1, panel 0, change screen 0, network exactly
`GET /admin/api/me`; served == merged (container bundle hash == tree bundle hash); the viewer
face regression-checked (home bootstraps + renders catalog).

**Status: CLOSED — fixed, tested at the previously-missing surface, deployed, live-verified.**

the deployed container).** The Owner's GATE-3 sign-in at `/admin` was refused twice. The
working hypothesis on dispatch was that the mid-gate truncate's restore had covered catalogue,
artwork and media refs but **not** operator identity — i.e. that admin access had been lost
silently and was merely *presenting* as an ordinary wrong-password refusal. **That hypothesis
was tested and falsified.** It is recorded here because it is the plausible-and-wrong reading
this failure mode invites, and the next person will reach for it too.

**Evidence (read-only; no credential value, plaintext or hash, printed or handled).**
- `admin_users` holds **exactly one row**, `michael@journeyviral.com`, `created_at`
  `2026-07-30 18:36:08.444`, `must_change_password = true`, `password_changed_at` NULL,
  `last_login_at` NULL. Its `tenant_id` resolves to slug `binjreel` — the same tenant
  `DEFAULT_TENANT_SLUG` resolves to in the running container, so the row sits where the login
  path looks. Hash shape verified without disclosure: 60 chars, `^\$2[aby]\$12\$` → bcrypt
  cost 12, intact.
- The restore **did** cover operator identity. The admin row was re-created at 18:36:08 in the
  same 2026-07-30 rebuild window as `tenants`/`series`/`episodes` (18:30:40).
- The live hash is **byte-identical to the committed seed literal** (compared by md5 digest;
  neither value printed). `prisma/seed.ts`'s admin block is untouched since `cd0d55e` (v0.4,
  2026-07-28) and its upsert carries `update: {}`, so a re-seed cannot overwrite an existing
  admin. **The temp credential in force is the same one issued at v0.4** — not lost, not
  rotated. STATE's "the temp credential remains untouched" reads true.
- Container log, two-hour window: exactly two events, both `POST /v1/admin-auth/login` from
  `172.18.0.5` (the `binjreel-web` proxy — that path is reaching the API), 16:18:59Z and
  16:19:20Z, each `access_refused` / `code: unauthorized` / `reason: "Sign-in failed"` / **401**.
  **Zero 429s** — the five raw `429` substring hits in the log were digits inside epoch
  timestamps and `responseTime` floats, not statuses. Across the container's full 20-hour life
  these are the *only* admin-auth requests ever made: two attempts, not a lockout.

**Named cause (the post-contrary-test finding).** Two distinct things, neither of them a lost
identity:
1. **The refusal is a genuine credential mismatch** — the value submitted did not match the
   seeded temp credential. Every server-side precondition for a successful login is present and
   correct.
2. **The log is structurally incapable of naming which branch refused, by design.**
   `src/admin/auth.ts:72` runs a real bcrypt compare against a boot-generated burn-in hash when
   the email is not found, and `adminAuth.ts:58` maps malformed input to the identical 401. So
   unknown-email, wrong-password and malformed-email are one indistinguishable event in both
   message and response time. That uniformity is correct security (it is what stops email
   enumeration) and it is **also** why a diagnosis cannot be read off the log alone — the DB and
   the seed had to be interrogated to close the question. Operator-facing symptom and
   attacker-facing opacity are the same property; no fix is wanted here, only awareness.

**Fix.** None applied, and none needed — nothing on the server is broken, so **nothing was
changed**. No row created, no hash written, no password generated. The Owner's recovery path is
to re-enter the v0.4 temp credential; the candidates for the mismatch are a garbled temp value
(it transited chat), autofill substituting a different saved password, or a malformed email
field. The forced first-login change remains armed and untouched.

**Standing correction (doctrine, carried forward as prevention — NOT this incident's cause).**
A restore or re-seed checklist must cover **identity tables**, not only viewer-visible data.
Catalogue, artwork and media refs are the visible surface, so their restoration is
self-evidencing — a missing operator row is silent until someone tries to sign in, and then it
presents as an ordinary wrong-password refusal that invites exactly the wrong conclusion. On
this occasion the seed's idempotent upsert happened to carry identity through; that was a
property of `seed.ts`, not of a checklist, and it should not be relied on as one.

**Also observed, not fixed here (record gap).** `DL-B009` was assigned and closed during the
restyle engagement (the raw `<video>` responder defect) but was never entered in this ledger —
it exists only in `BUILD-LEDGER.md` L-044. This entry therefore takes `DL-B010`. The missing
B009 entry is raised, not closed.

**Status: CLOSED — investigated, hypothesis falsified, not a defect; no change made.**

## DL-B009 · 2026-07-30 · Continue-Watching tap went to the wrong screen — and opening an episode destroyed its resume mark
*Entered retroactively 2026-07-31. Assigned and fixed during the conformance-completion engagement
(`BUILD-LEDGER.md` L-044 §5, commit `5c612eb`) but never written into this ledger — the gap is the
reason `DL-B010` was already taken by the sign-in diagnosis before this entry existed. Transcribed
from L-044; not re-verified in the close-out order.*

**What happened.** Continue Watching was the shelf that was supposed to prove the product's core
loop — leave mid-episode, come back, resume. It failed at both ends, and the two failures masked
each other: the tap never reached the player, so the destroyed resume mark was invisible.

**Half (a) — the nested Pressable stole the gesture.** `PosterCard` is itself a `Pressable`.
Nesting it inside the Continue Watching `Pressable` meant the INNER one won the gesture on web, so
**every tap landed on the show page, never the player**. Fixed by a `nested` prop that renders the
card as a plain `View`, leaving exactly one responder in the tree.

**Half (b) — the mount-time progress write destroyed the stored mark.** The card navigated without
`?t=`, and the player's mount-time `POST /progress` then posted that `0` back. So merely OPENING an
episode **overwrote its resume position with zero** — the data the shelf existed to display was
being erased by the act of using the shelf. Fixed by having the player learn `seriesId` from the
prefetched `/next` payload instead of writing to find out, falling back to the first real progress
tick on a series' final episode.

**Named cause (the traceback).** Both halves are the same root: **a read was implemented as a
write.** (b) is that literally — the player needed `seriesId`, and the cheapest way to obtain it was
to POST progress and read the response, so a lookup was expressed as a mutation against the very
row the feature depends on. (a) is its interaction twin — a component that is already an interactive
element was composed INSIDE another interactive element, so ownership of the gesture was decided by
framework precedence rather than by design. Neither could be caught by the existing suites, because
nothing tested what a browser does with a real tap on a real shelf; the resume loop had only ever
been exercised at the API.

**Fix.** `nested` prop on `PosterCard` (one responder per card) · player derives `seriesId` from the
`/next` prefetch, never from a mount-time write · **`web/e2e/resume.spec.mjs` added — the
previously-missing test class**, driving the real exported bundle in a real browser at **390 and
1440**: lands on `/watch/{id}?t=6`, seeks, autoplays, and asserts the resume pointer SURVIVES the
visit. 2/2. Real Chrome, not bundled Chromium — the latter has no H.264, so the stage would capture
as a still and "did it resume" would be unobservable.

**Status: CLOSED — both halves fixed, verified live at 390 and 1440, regression-guarded by a new
e2e class.**

## DL-B011 · 2026-07-30 · The test suite could TRUNCATE the live production database — and did
*Entered retroactively 2026-07-31, transcribed from `BUILD-LEDGER.md` L-044 §7. Numbered B011
because B010 was taken by the sign-in diagnosis on 2026-07-31; B009 is entered above.*

**What happened.** `resetDatabase()` in `test/helpers.ts` TRUNCATEs **every** table including
`tenants`. Running the API suite through the `app` compose service inherits the **live**
`DATABASE_URL`. Doing exactly that mid-gate **destroyed the deployed catalog, the operator account
and every media ref** on the production database. The site could not mint sessions:
`/v1/auth/anonymous` began 500ing on a dangling tenant FK. This was not a near-miss — production
data was lost and had to be rebuilt.

**Restored at the time.** Reseeded; the app restarted so it would re-resolve the tenant; the one
real Bunny clip (`b56ffcb4-6df8-4ce6-81e3-1ef908384ebf`) re-attached to *Fired & Furious* ep 1; and
the suite's placeholder `bunny_ref`s cleared so no episode advertised media that would 404.

**Named cause (the traceback).** **Destructive power was ambient, and the only thing standing
between it and production was which environment a developer happened to invoke it from.**
`resetDatabase()` asserted nothing about WHERE it was pointed — it trusted `DATABASE_URL`, and
`DATABASE_URL` is correct for the app and catastrophic for the suite. A test helper that can
TRUNCATE `tenants` is production-destroying code shipped in the test tree, where it reads as
harmless. The guard that was missing is not "be careful which service you run" — a convention no
tooling enforces is not a control.

**Fix.** `test/helpers.ts` now **refuses to truncate any database not named like a test database**,
with an explicit `ALLOW_DESTRUCTIVE_DB_RESET=1` override for the rare deliberate case — **proven to
fail closed against `binjreel`**, not merely asserted. A compose `test` service runs the suite
against `${POSTGRES_DB}_test`, so the isolated database is the default path rather than a thing to
remember:

```
docker compose run --rm test          # 147/147, isolated database
```

**`docker compose run --rm test` is now the only way the suite runs.**

**Residue, now cleared.** Two artifacts the destructive run left in the live database — a duplicate
shelf `slug='new'` and a draft series `Unannounced Pilot`, neither created by `prisma/seed.ts` —
were deliberately NOT deleted unilaterally, since removing them is a destructive write to production
data. The Owner approved the exact SQL, and it was executed at v0.4 GATE-3 close on 2026-07-31:
`shelves` 7→6, `shelf_items` 32→30, `series` 12→11, `episodes` 83→82 (cascade), with Home, anonymous
session minting and *Fired & Furious* ep 1 media all re-verified live afterwards. Full record:
`BUILD-LEDGER.md` L-046.

**Standing correction.** The identity-table lesson recorded under DL-B010 is the same incident seen
from the other side: this truncate is what destroyed the operator row, and the restore's coverage of
it was a property of the seed's idempotent upsert rather than of any checklist. A restore or
re-seed checklist must cover **identity tables**, not only viewer-visible data.

**Status: CLOSED — guarded at the helper (fail-closed, proven), isolated by default at the compose
layer, and the production residue cleared under Owner approval.**
